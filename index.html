1. Scope

1.1 What This Reference Specifies

This reference specifies the following aspects of the Zeuz programming language:

  1. The lexical structure of source files with extension .zz.
  2. The grammar of Zeuz programs, expressed in Extended Backus-Naur Form (EBNF).
  3. The static semantics of Zeuz programs, that is, the constraints that a well-formed program MUST satisfy and that a conforming implementation MUST diagnose.
  4. The dynamic semantics of Zeuz programs, that is, the observable behavior of a well-formed program when executed.
  5. The memory model, including allocation, lifetime, aliasing, and the guarantees that the language does and does not make.
  6. The interface of the built-in functions print, len, input, and assert.
  7. The program structure required for a program to be executable, in particular the requirement for a function named entryf.

1.2 What This Reference Does Not Specify

This reference does not specify:

  1. The application binary interface (ABI) of a compiled Zeuz binary, including calling conventions, stack layout, and register usage. These are implementation-defined.
  2. The behavior of any linker or assembler invoked by the compiler toolchain.
  3. The optimizations performed by the implementation. A conforming implementation MAY emit any code whose observable behavior matches the behavior specified in this document.
  4. The presence, content, or format of debug information, unless stated otherwise.
  5. The behavior of a program that exhibits undefined behavior as listed in Section 13.4.
  6. The behavior of a program whose resource consumption exceeds the limits of the host system.
  7. The textual format of diagnostic messages. A conforming implementation MUST emit a diagnostic, but the content of the message is implementation-defined.

2. Normative References

The following documents are referenced normatively. Implementations MUST interpret terms defined in this reference according to the referenced documents where this reference is silent.

2.1 LLVM Language Reference Manual. The implementation uses LLVM as its code generation backend. The semantics of the generated LLVM IR, including the semantics of integer arithmetic, floating-point arithmetic, and memory operations, are defined by the LLVM Language Reference. Where this reference specifies a behavior different from the LLVM behavior (for example, division by zero, see Section 8.6.9), this reference takes precedence and the implementation MUST insert the necessary runtime checks.

2.2 ISO/IEC 9899 (C standard). The built-in functions of Zeuz delegate to the corresponding C standard library functions. The observable behavior of the following C functions, as invoked by the Zeuz runtime helpers, is defined by the C standard and by the C library on the target platform: printf, malloc, memcpy, memset, strlen, strcmp, snprintf, fgets, fputs, fflush, exit, floor. In addition, the objects stdin, stdout, and stderr are the C standard streams.

2.3 IEEE 754-2019. The representation and arithmetic behavior of the type float are those of IEEE 754 binary64 (double precision), except where explicitly restricted in Section 7.1.3.

2.4 RFC 2119. Key words for use in RFCs to indicate requirement levels.

3. Terms and Definitions

For the purposes of this document, the following terms apply.

3.1 Source file. A sequence of bytes with the extension .zz that is supplied to the compiler as input.

3.2 Compilation unit. The sequence of tokens produced by the lexer from a single source file, together with the abstract syntax tree produced by the parser from those tokens. A compilation unit corresponds to exactly one source file. Zeuz 1.0 has no mechanism for combining multiple compilation units.

3.3 Program. A compilation unit that has been successfully parsed and has passed static semantic analysis. A program is the unit of compilation.

3.4 Well-formed program. A program that satisfies every constraint defined in this reference. A conforming implementation MUST accept every well-formed program.

3.5 Ill-formed program. A program that violates at least one constraint defined in this reference. A conforming implementation MUST reject every ill-formed program and MUST emit at least one diagnostic message. The point at which rejection occurs (during lexing, parsing, static analysis, or code generation) is implementation-defined.

3.6 Undefined behavior. Behavior for which this reference imposes no requirements. A program that exhibits undefined behavior has no defined output, exit code, or side effect. Section 13.4 lists the conditions that produce undefined behavior in Zeuz 1.0.

3.7 Implementation-defined behavior. Behavior for which this reference requires the implementation to choose a behavior but does not mandate a specific choice. The implementation MUST document its choice. Section 13.5 lists the implementation-defined behaviors of Zeuz 1.0.

3.8 Unspecified behavior. Behavior for which this reference provides two or more permissible outcomes and does not require the implementation to document which outcome occurs. Zeuz 1.0 does not introduce unspecified behavior beyond what is inherited from the C standard library.

3.9 Diagnostic message. A message emitted by a conforming implementation in response to an ill-formed program. A diagnostic message MUST identify the source file and SHOULD identify the line and column of the offending construct.

3.10 Observable behavior. The sequence of bytes written to the standard output stream, the sequence of bytes written to the standard error stream, and the exit code of the process.

3.11 Value. A member of the set {integer value, floating-point value, string value, void value} as defined in Section 7.

3.12 Lvalue. An expression that denotes a storage location. In Zeuz 1.0, the only expressions that denote storage locations are variable references and array index expressions when used as the target of an assignment.

3.13 Truthy. A value is truthy if it is an integer value not equal to zero, a floating-point value not equal to 0.0, or a string value with at least one character. The boolean value false and the integer value zero are not truthy. See Section 8.6.7.

3.14 Entry point function. A function declaration with the identifier entryf and the return type void, whose body is executed at program startup. See Section 13.2.

3.15 Runtime helper. A function emitted by the implementation into the generated module, with an identifier beginning with zz_, that provides a service required by the semantics of a built-in or operator. Runtime helpers are not part of the source language surface syntax and MUST NOT be referenced by a Zeuz program.

4. Conformance

4.1 Conforming Implementation

An implementation conforms to this reference if and only if:

  1. It accepts every well-formed program, as defined in this reference, and produces an executable whose observable behavior matches the behavior specified in this document.
  2. It rejects every ill-formed program, as defined in this reference, and emits at least one diagnostic message.
  3. It documents every implementation-defined behavior listed in Section 13.5.
  4. It does not silently accept any construct that this reference declares ill-formed.

4.2 Extensions

4.2.1 An implementation MAY accept source text that is not covered by this reference, provided that the acceptance of such source text does not alter the observable behavior of any well-formed program that does not use the extension.

4.2.2 An implementation that provides extensions MUST document them and MUST provide a mode in which the extensions are rejected.

4.2.3 In this revision of the reference, Zeuz 1.0 defines no extensions. All constructs listed in Section 5.7 as Reserved Keywords MUST be rejected when used in a position where a statement is expected.

4.3 Quality of Implementation

The following are not conformance requirements and are listed for information:

  • An implementation SHOULD report the line and column of the first error it encounters.
  • An implementation SHOULD NOT produce a partial binary when compilation fails.
  • An implementation SHOULD reject every program in which a variable is used before it is initialized.

5. Lexical Structure

5.1 Source Encoding

5.1.1 A source file MUST be encoded as a sequence of bytes. The implementation MUST interpret the bytes as UTF-8 encoded text for the purpose of extracting tokens.

5.1.2 A byte sequence that is not valid UTF-8 yields implementation-defined behavior. Implementations SHOULD report a diagnostic.

5.1.3 Non-ASCII characters MAY appear inside string literals and character literals. Their interpretation is implementation-defined. In the reference implementation of Zeuz 1.0, non-ASCII bytes in a string literal are copied verbatim into the string's runtime representation. The behavior of len() on such a string counts bytes, not characters.

5.1.4 A source file MAY begin with a UTF-8 byte order mark (U+FEFF). If present, the implementation MUST skip it. The byte order mark is not a token.

5.2 Whitespace

5.2.1 The following characters are whitespace: space (U+0020), horizontal tab (U+0009), carriage return (U+000D), and line feed (U+000A).

5.2.2 Whitespace characters separate tokens and are otherwise ignored. A sequence of one or more whitespace characters is equivalent to a single whitespace character.

5.2.3 Line endings. A line feed (U+000A) terminates a line. A carriage return followed by a line feed (U+000D U+000A) also terminates a line and is treated as a single line terminator. A standalone carriage return (U+000D) is treated as whitespace but does not terminate a line.

5.2.4 The implementation MUST track line and column numbers for diagnostic purposes, but the exact column at which a token is reported is implementation-defined.

5.3 Comments

5.3.1 A line comment begins with the sequence // (U+002F U+002F) and extends to, but does not include, the next line terminator. A line comment is replaced by a single whitespace character.

5.3.2 A block comment begins with the sequence /* (U+002F U+002A) and ends with the sequence */ (U+002A U+002F). A block comment is replaced by a single whitespace character.

5.3.3 Block comments nest. Each occurrence of /* within a block comment increments the nesting level. Each occurrence of */ decrements the nesting level. The comment terminates when the nesting level reaches zero. A block comment that reaches the end of the source file without terminating is ill-formed and MUST be diagnosed.

5.3.4 The tokens // and /* are recognized at any point where a token may begin. A // inside a string literal or a character literal is part of the literal, not a comment.

5.4 Tokens

5.4.1 The lexer partitions the source file into a sequence of tokens. Each token belongs to exactly one of the following categories: keyword, identifier, integer literal, float literal, string literal, character literal, operator, punctuator.

5.4.2 The lexer MUST produce the longest match at each position. For example, the sequence == MUST be lexed as the equality operator, not as two assignment operators.

5.4.3 A token that is not recognized as belonging to any category above is ill-formed and MUST be diagnosed.

5.5 Identifiers

5.5.1 An identifier is a sequence of one or more identifier characters.

5.5.2 The identifier characters are: a through z, A through Z, 0 through 9, and the underscore character _.

5.5.3 The first character of an identifier MUST be a through z, A through Z, or _. The first character MUST NOT be a digit.

5.5.4 Identifiers are case-sensitive. foo, Foo, and FOO denote three distinct identifiers.

5.5.5 The grammar for an identifier is:

Identifier      ::= IdentifierStart IdentifierChar*
IdentifierStart ::= "a"..."z" | "A"..."Z" | "_"
IdentifierChar  ::= IdentifierStart | "0"..."9"

5.5.6 An identifier that matches a keyword listed in Section 5.6 is lexed as a keyword, not as an identifier. An identifier that matches a reserved keyword listed in Section 5.7 is lexed as a keyword and is subject to the constraints of Section 5.7.

5.5.7 An identifier MAY be of any length. The reference implementation of Zeuz 1.0 imposes no upper bound.

5.6 Keywords

5.6.1 The following identifiers are keywords that are recognized by the parser and that have a defined meaning in Zeuz 1.0:

  • Control-flow keywords: if, else, while, for, do, loop, break, continue, return.
  • Statement keywords: print, assert.
  • Literal keywords: true, false, null, nullptr, inf, nan.
  • Type-name keywords: int, float, string, void, bool, char, byte, i8, i16, i32, i64, i128, u8, u16, u32, u64, u128, usize, isize, f16, f32, f64.

5.6.2 A keyword MUST NOT be used as an identifier in any declaration. Using a keyword as an identifier is ill-formed.

5.7 Reserved Keywords

5.7.1 The following identifiers are lexed as keywords but do not have a defined meaning in Zeuz 1.0. They are reserved for future versions of the language. A source file that uses any of these keywords in any position is ill-formed and MUST be diagnosed with an implementation-defined message.

5.7.2 Reserved keywords, grouped by intended future feature:

  • Pattern matching: match, case, default.
  • Error handling and deferral: guard, defer, try, catch, finally, throw, panic, recover.
  • Module system: import, namespace, export, pub, extern.
  • Macro system: macro.
  • Declaration forms: fn, let, var, const, type.
  • Object-orientation: class, trait, impl, extends, super, this, self, interface, struct, enum.
  • Concurrency: async, await, spawn, join, lock, unlock, atomic, sync.
  • Pointer and reference syntax: ptr, rawptr, ref, new, delete, move.
  • Type operators: sizeof, typeof.
  • Storage and safety attributes: unsafe, asm, in, as, pad, reusable, simd, recursive, thread_fn, varint, any, auto.
  • Miscellaneous: arr, slice, yield, goto, block.

5.7.3 The keyword do is used by the do-while statement (Section 9.6) and is therefore not in the reserved list. The keyword block is reserved and MUST be diagnosed. An earlier draft of this reference incorrectly listed do as reserved; this draft corrects the error.

5.7.4 The reference implementation of Zeuz 1.0 rejects every reserved keyword except do, which is a recognized keyword, and the type-name keywords and literal keywords listed in Section 5.6.1, which are recognized. All other keywords that are lexed but not handled by the parser produce a diagnostic of the form '<keyword>' statement not yet implemented or '<keyword>' declarations not yet implemented.

5.8 Integer Literals

5.8.1 An integer literal is a sequence of one or more decimal digits.

5.8.2 Zeuz 1.0 does not support hexadecimal, octal, or binary integer literals. A leading 0 is permitted and does not change the meaning; 042 denotes the integer value forty-two.

5.8.3 The grammar for an integer literal is:

IntegerLiteral ::= Digit+
Digit          ::= "0"..."9"

5.8.4 The value of an integer literal is the mathematical value of the digit sequence, interpreted as a signed 64-bit integer. If the mathematical value is not representable in a signed 64-bit integer, the program is ill-formed and MUST be diagnosed.

5.8.5 A negative integer literal such as -1 is lexed as two tokens: the unary minus operator - followed by the integer literal 1. The parser then forms a unary expression. See Section 8.7.

5.9 Float Literals

5.9.1 A float literal is a sequence of one or more decimal digits, followed by a single period ., followed by one or more decimal digits.

5.9.2 Zeuz 1.0 does not support exponent notation such as 1e10. A float literal that does not contain a decimal point is lexed as an integer literal, not a float literal.

5.9.3 The grammar for a float literal is:

FloatLiteral ::= Digit+ "." Digit+

5.9.4 The value of a float literal is the mathematical value of the digit sequence, rounded to the nearest representable value in IEEE 754 binary64. The rounding mode is implementation-defined.

5.9.5 A float literal whose magnitude exceeds the range of IEEE 754 binary64 is ill-formed and MUST be diagnosed.

5.9.6 A negative float literal such as -3.14 is lexed as the unary minus operator followed by the float literal 3.14.

5.10 String Literals

5.10.1 A string literal begins with a double quote " (U+0022) and ends with a double quote. Between the quotes, zero or more string characters appear.

5.10.2 A string character is any byte except " (U+0022), \ (U+005C), or a line terminator, unless it is part of an escape sequence.

5.10.3 The following escape sequences are recognized:

  • \n produces the line feed character (U+000A).
  • \t produces the horizontal tab character (U+0009).
  • \r produces the carriage return character (U+000D).
  • \\ produces the backslash character (U+005C).
  • \" produces the double quote character (U+0022).

5.10.4 An escape sequence not listed in Section 5.10.3 is ill-formed and MUST be diagnosed. In particular, \0, \', \x, and \u are not recognized.

5.10.5 A string literal that contains an unescaped line terminator is ill-formed. Zeuz 1.0 does not support multiline string literals.

5.10.6 The grammar for a string literal is:

StringLiteral   ::= '"' StringChar* '"'
StringChar      ::= any byte except '"', '\\', or line terminator
                  | EscapeSequence
EscapeSequence  ::= "\\" ( "n" | "t" | "r" | "\\" | '"' )

5.10.7 The runtime representation of a string is a null-terminated byte sequence. See Section 12.5.

5.11 Character Literals

5.11.1 A character literal begins with a single quote ' (U+0027) and ends with a single quote. Between the quotes, exactly one character appears, which may be an escape sequence.

5.11.2 The escape sequences recognized inside a character literal are \n, \t, \r, \\, \', and \0. The first five correspond to the same byte values as in Section 5.10.3. \0 produces the null byte (U+0000).

5.11.3 The value of a character literal is the integer value of the byte it contains, in the range 0 to 255 inclusive. Character literals have type int.

5.11.4 The grammar for a character literal is:

CharLiteral    ::= "'" CharBody "'"
CharBody       ::= SingleChar | CharEscape
SingleChar     ::= any byte except "'", '\\', or line terminator
CharEscape     ::= "\\" ( "n" | "t" | "r" | "\\" | "'" | "0" )

5.11.5 A character literal that contains zero characters, or more than one character, is ill-formed and MUST be diagnosed.

5.12 Boolean and Null Literals

5.12.1 The keywords true and false denote the integer values one and zero respectively. They have type int.

5.12.2 The keywords null and nullptr denote the integer value zero. They have type int.

5.13 Special Float Literals

5.13.1 The keyword inf denotes the IEEE 754 positive infinity value. It has type float.

5.13.2 The keyword nan denotes the IEEE 754 quiet NaN value. It has type float.

5.13.3 The unary minus operator applied to inf produces negative infinity. The unary minus operator applied to nan produces a NaN, but whether the sign bit is preserved is implementation-defined.

5.14 Operators

5.14.1 The following two-character operator tokens are recognized:

==   !=   <=   >=   &&   ||

5.14.2 The following single-character operator tokens are recognized:

+   -   *   /   =   !   <   >

5.14.3 The following characters are NOT operators in Zeuz 1.0 and are ill-formed when they appear where an operator is expected: %, &, |, ^, ~, ?, :, ., #, @, $.

5.14.4 The implementation MUST lex == as a single token even when the surrounding whitespace would allow reading = = as two tokens. The longest-match rule of Section 5.4.2 applies.

5.15 Punctuators

5.15.1 The following punctuator tokens are recognized:

(   )   {   }   [   ]   ;   ,

5.15.2 No other punctuator tokens exist in Zeuz 1.0.

5.15.3 The implementation MUST lex each punctuator as a single-character token except where a two-character operator would be the longest match (which never occurs for punctuators).

6. Grammar (EBNF)

6.1 Notation

6.1.1 The grammar in this section uses Extended Backus-Naur Form (EBNF) with the following conventions:

  • A production has the form Name ::= Definition.
  • Alternatives are separated by |.
  • Parentheses group alternatives.
  • A postfix * indicates zero or more occurrences.
  • A postfix + indicates one or more occurrences.
  • A postfix ? indicates zero or one occurrence.
  • Terminal tokens appear in double quotes.

6.1.2 Whitespace and comments are removed by the lexer before parsing (Section 5.2, Section 5.3). The grammar in this section is a grammar over the token stream, not over characters.

6.1.3 Every production is assigned a number in the form G.n.m, where n is the section number and m is a sequence number within the section.

6.2 Program Structure Productions

G.6.2.1  Program      ::= TopLevelDecl*
G.6.2.2  TopLevelDecl ::= FunctionDecl | Statement

6.2.1 A program is a sequence of top-level declarations. Each top-level declaration is either a function declaration or a statement.

6.2.2 A program MUST contain exactly one function declaration whose name is entryf. See Section 13.2.

6.3 Declaration Productions

G.6.3.1  FunctionDecl ::= TypeName Identifier "(" ParamList? ")" Block
G.6.3.2  ParamList    ::= Param ( "," Param )*
G.6.3.3  Param        ::= TypeName Identifier "[" "]"?
G.6.3.4  VarDecl      ::= TypeName Identifier ( "[" Expression "]" ( "=" "{" ArrayInit? "}" )? | "=" Expression )? ";"
G.6.3.5  ArrayInit    ::= Expression ( "," Expression )*

6.3.1 A function declaration consists of a return type, an identifier, a parameter list, and a body. The body MUST be a block (Section 6.4.2).

6.3.2 A parameter list MAY be empty.

6.3.3 A parameter is either a scalar parameter (TypeName Identifier) or an array parameter (TypeName Identifier []). An array parameter is passed as a pointer to the first element; the length is not passed. See Section 9.13.4 and Section 12.4.3.

6.3.4 A variable declaration consists of a type name, an identifier, and one of: an array size expression in square brackets optionally followed by an initializer list in braces; an optional initializer expression introduced by =; or neither, in which case the variable is default-initialized (Section 9.1.2). The declaration MUST be terminated by a semicolon.

6.4 Statement Productions

G.6.4.1   Statement    ::= VarDecl
                        | Block
                        | IfStatement
                        | WhileStatement
                        | DoWhileStatement
                        | ForStatement
                        | LoopStatement
                        | ReturnStatement
                        | PrintStatement
                        | AssertStatement
                        | BreakStatement
                        | ContinueStatement
                        | ExprStatement
                        | FunctionDecl
G.6.4.2   Block        ::= "{" Statement* "}"
G.6.4.3   IfStatement  ::= "if" "(" Expression ")" Statement ( "else" Statement )?
G.6.4.4   WhileStatement ::= "while" "(" Expression ")" Statement
G.6.4.5   DoWhileStatement ::= "do" Statement "while" "(" Expression ")" ";"
G.6.4.6   ForStatement ::= "for" "(" ForInit? ";" Expression? ";" Expression? ")" Statement
G.6.4.7   ForInit      ::= VarDecl | ExprStatement
G.6.4.8   LoopStatement ::= "loop" Statement
G.6.4.9   ReturnStatement ::= "return" Expression? ";"
G.6.4.10  PrintStatement ::= "print" Expression ";"
G.6.4.11  AssertStatement ::= "assert" "(" Expression ")" ";"
G.6.4.12  BreakStatement ::= "break" ";"
G.6.4.13  ContinueStatement ::= "continue" ";"
G.6.4.14  ExprStatement ::= Expression ";"

6.5 Expression Productions

G.6.5.1   Expression     ::= LogicalOr
G.6.5.2   LogicalOr      ::= LogicalAnd ( "||" LogicalAnd )*
G.6.5.3   LogicalAnd     ::= Equality ( "&&" Equality )*
G.6.5.4   Equality       ::= Comparison ( ( "==" | "!=" ) Comparison )*
G.6.5.5   Comparison     ::= Additive ( ( "<" | ">" | "<=" | ">=" ) Additive )*
G.6.5.6   Additive       ::= Multiplicative ( ( "+" | "-" ) Multiplicative )*
G.6.5.7   Multiplicative ::= Unary ( ( "*" | "/" ) Unary )*
G.6.5.8   Unary          ::= ( "-" | "!" ) Unary
                          | Cast
                          | Postfix
G.6.5.9   Cast           ::= "(" TypeName ")" Unary
G.6.5.10  Postfix        ::= Primary PostfixSuffix*
G.6.5.11  PostfixSuffix  ::= "(" ArgList? ")"
                          | "[" Expression "]"
                          | "=" Expression
G.6.5.12  ArgList        ::= Expression ( "," Expression )*
G.6.5.13  Primary        ::= IntegerLiteral
                          | FloatLiteral
                          | StringLiteral
                          | CharLiteral
                          | "true" | "false" | "null" | "nullptr"
                          | "inf" | "nan"
                          | Identifier
                          | "(" Expression ")"
G.6.5.14  TypeName       ::= "int" | "float" | "string" | "void"
                          | "bool" | "char" | "byte"
                          | "i8" | "i16" | "i32" | "i64" | "i128"
                          | "u8" | "u16" | "u32" | "u64" | "u128"
                          | "usize" | "isize"
                          | "f16" | "f32" | "f64"

6.6 Precedence Cross-Reference

6.6.1 The grammar in Section 6.5 encodes the precedence of operators by the nesting of productions. A production that appears lower in the list binds more tightly. The precedence table is reproduced in Appendix C.

6.6.2 All binary operators are left-associative. The grammar encodes this by using left recursion in the *-repetition form.

6.6.3 The unary operators - and !, and the cast operator, are right-associative and bind tighter than the additive operators.

6.6.4 Postfix operators (call, index, assignment) bind tighter than unary operators.

6.6.5 The assignment operator = in G.6.5.11 is only permitted when the target of the postfix chain is a variable reference or an array index expression. See Section 8.8.

7. Types and Type System

7.1 Primitive Types

7.1.1 Zeuz 1.0 has exactly four primitive types: int, float, string, and void.

7.1.2 The type int represents a signed 64-bit integer. The representation is two's complement. The range of representable values is -2^63 to 2^63 - 1 inclusive. See Section 14.2 for the rationale.

7.1.3 The type float represents an IEEE 754 binary64 floating-point value. The special values positive infinity, negative infinity, and NaN are representable and observable through the keywords inf and nan and through arithmetic operations that produce them.

7.1.4 The type string represents a pointer to a null-terminated byte sequence in heap storage. The byte sequence is not bounded by any length field; its length is computed by scanning for the null terminator. See Section 12.5.

7.1.5 The type void is the type of expressions that produce no value and of function declarations that return no value. An expression of type void MUST NOT appear as an operand of any operator, as an argument to a function call, or as the value of a variable declaration.

7.2 Integer Type Aliases

7.2.1 The following type names denote exactly the same type as int: bool, char, byte, i8, i16, i32, i64, i128, u8, u16, u32, u64, u128, usize, isize.

7.2.2 The width implied by these names MUST NOT be enforced by the implementation. In particular, a variable declared u8 x = 300; MUST be accepted and MUST store the value 300. Similarly, a variable declared i8 x = -200; MUST be accepted and MUST store the value -200. This is a deliberate simplification of the type system. See Section 14.2.

7.2.3 The signedness implied by these names (for example, the distinction between i32 and u32) MUST NOT be enforced. All integer operations are performed as signed 64-bit operations.

7.3 Float Type Aliases

7.3.1 The following type names denote exactly the same type as float: f16, f32, f64.

7.3.2 The width implied by these names MUST NOT be enforced by the implementation. A variable declared f16 x = 3.14; stores the full IEEE 754 binary64 value of 3.14, not a value rounded to half precision.

7.4 The void Type

7.4.1 The type void is used only as the return type of a function declaration. Declaring a variable of type void is ill-formed and MUST be diagnosed.

7.4.2 A function declared with return type void MUST NOT contain a return statement with an operand. A return statement without an operand in a void function is well-formed.

7.4.3 The type of a call expression to a void function is void. Using such a call expression as an operand of any operator is ill-formed.

7.5 Type Compatibility

7.5.1 Two types are compatible if and only if they are the same type, or if both are integer aliases (Section 7.2), or if both are float aliases (Section 7.3).

7.5.2 An assignment of a value of type float to a variable of type int is ill-formed and MUST be diagnosed. This is a static check, not a runtime check. See Section 8.8.1.4.

7.5.3 An assignment of a value of type int to a variable of type float is well-formed and performs an implicit widening conversion from int to float. See Section 8.8.1.3.

7.5.4 An assignment of a value of type string to a variable of type string is well-formed. Assignments between string and any other type are ill-formed.

7.5.5 An assignment of a value of any type to a variable of type void is ill-formed.

7.6 Type Inference

7.6.1 Zeuz 1.0 does not perform type inference. Every variable declaration MUST include an explicit type name. The type of a variable is the type declared. See Section 9.1.

7.6.2 The type of an expression is computed by the rules in Section 8. The type of a function's return value is declared explicitly in the function declaration. No inference occurs.

7.7 Casting Rules

7.7.1 The cast expression (TypeName) Expr converts the value of Expr to the named type, provided the conversion is defined. The following conversions are defined:

  • (int) f where f has type float: converts the float to an integer by truncating toward zero. If f is NaN, infinity, or outside the range of a signed 64-bit integer, the result is implementation-defined.
  • (float) i where i has type int: converts the integer to a float. The conversion is exact for values in the range -2^53 to 2^53 inclusive.
  • (string) i where i has type int: converts the integer to its decimal representation as a string, allocated on the heap.
  • (string) f where f has type float: converts the float to a string. If the float is finite and has no fractional part, the result has the form N.0. Otherwise the result has the form produced by the C printf("%g") format.

7.7.2 A cast to the same type as the operand produces the operand unchanged. A cast from string to any other type is ill-formed and MUST be diagnosed. A cast from void to any type is ill-formed.

7.7.3 A cast expression does not change the source-level type of the operand for the purpose of static checks elsewhere in the program.

8. Expressions

8.1 Integer Literals

8.1.1 An integer literal denotes a value of type int. The value is computed according to Section 5.8.4.

8.1.2 The type of an integer literal is int, regardless of the number of digits. There is no separate type for large literals.

8.1.3 Example:

int x = 42;      // x has value 42
int y = 0;       // y has value 0
int z = 042;     // z has value 42; leading zero is permitted and ignored

8.2 Float Literals

8.2.1 A float literal denotes a value of type float. The value is computed according to Section 5.9.4.

8.2.2 The type of a float literal is float, regardless of whether the value is integral (for example, 1.0 has type float, not int).

8.2.3 A float literal MUST contain a decimal point followed by at least one digit. The token 1. and the token .5 are ill-formed. 1.0 and 0.5 are well-formed.

8.2.4 Example:

float a = 3.14;    // a has value 3.14
float b = 1.0;     // b has value 1.0, type float
float c = -2.5;    // parsed as unary minus applied to 2.5

8.3 String Literals

8.3.1 A string literal denotes a value of type string. The value is a pointer to a null-terminated byte sequence allocated in heap storage at the point where the literal is evaluated.

8.3.2 Each evaluation of a string literal produces a pointer to the same byte sequence. The implementation MAY allocate the byte sequence once at program start and reuse the pointer for every evaluation of the same literal, or MAY allocate a fresh copy on each evaluation. Both behaviors are conforming. A program MUST NOT rely on either behavior, except that the byte sequence is immutable and the pointer is valid for the lifetime of the process.

8.3.3 The byte sequence does not include the surrounding quotes. The byte sequence includes an implicit null terminator byte (value 0) immediately after the last byte of the literal content.

8.3.4 Example:

string s = "hello";          // s points to the bytes 'h' 'e' 'l' 'l' 'o' 0
string t = "line1\nline2";   // escape \n produces a newline byte (value 10)
string u = "";               // empty string, byte sequence is a single null byte

8.4 Character Literals

8.4.1 A character literal denotes a value of type int. The value is the integer value of the contained byte, in the range 0 to 255 inclusive.

8.4.2 Character literals are provided for readability. There is no separate char type at the semantic level. A character literal and the equivalent integer literal are interchangeable.

8.4.3 Example:

int a = 'A';    // a has value 65
int b = '\n';   // b has value 10
int c = '\0';   // c has value 0
int d = 'A' + 1; // d has value 66

8.5 Variable References

8.5.1 A variable reference is an identifier that denotes a variable in scope (Section 10).

8.5.2 When a variable reference appears in a context that requires a value (an rvalue context), it is evaluated to the current value of the variable. The type of the expression is the declared type of the variable.

8.5.3 When a variable reference appears as the target of an assignment (Section 8.8), it denotes the storage location of the variable, not its current value.

8.5.4 If the variable is an array (declared with an array size, or declared as an array parameter), using the variable name in a scalar context is ill-formed and MUST be diagnosed. The only permitted uses of an array variable name are:

  • As the target of an assignment expression of the form name = ..., which is ill-formed (Section 8.8.1.5).
  • As an argument to a function parameter declared as an array (Section 8.11.4).
  • As the argument to len() (Section 11.2).
  • As the argument to print (Section 11.1).
  • As the condition of an if, while, do-while, or for statement (Section 8.6.7).

8.5.5 Example:

int x = 5;
int y = x + 1;    // x is evaluated to 5; y is 6
x = 10;           // x denotes the storage location; 10 is stored
int z = x;        // z is 10

int arr[3];
int v = arr;      // ill-formed: array used in scalar context

8.6 Binary Operators

8.6.1 Overview

8.6.1.1 The binary operators are +, -, *, /, ==, !=, <, >, <=, >=, &&, ||.

8.6.1.2 The left operand is evaluated before the right operand. This order MUST be observed by the implementation. A program MAY rely on this order when the operands have side effects.

8.6.1.3 The precedence and associativity of binary operators are defined by Section 6.5 and reproduced in Appendix C.

8.6.2 Arithmetic Operators: +, -, *, /

8.6.2.1 If both operands have type int, the operator is an integer operation and the result has type int.

8.6.2.2 If at least one operand has type float, the operator is a floating-point operation. The int operand, if any, is implicitly converted to float by a widening conversion. The result has type float.

8.6.2.3 If either operand has type string, + is the string concatenation operator (Section 8.6.6). The operators -, *, and / applied to a string operand are ill-formed and MUST be diagnosed.

8.6.2.4 Integer overflow in +, -, or * is not detected. The behavior is to compute the result modulo 2^64 interpreted as a signed 64-bit integer. This is well-defined behavior for Zeuz 1.0. The implementation MUST NOT terminate the program on integer overflow.

8.6.2.5 Floating-point arithmetic follows IEEE 754 binary64 with round-to-nearest-even as the default rounding mode. Operations that produce infinity or NaN produce those values; the implementation MUST NOT terminate the program in that case.

8.6.2.6 Example:

int a = 7 + 3;         // a = 10
int b = 7 - 3;         // b = 4
int c = 7 * 3;         // c = 21
int d = 7 / 3;         // d = 2 (integer division truncates toward zero)
float e = 7.0 / 3.0;   // e is approximately 2.3333333333333335
float f = 7 / 3.0;     // f is approximately 2.3333333333333335; int 7 promoted

8.6.3 Comparison Operators on Numeric Operands: <, >, <=, >=

8.6.3.1 If both operands are numeric (int or float), the comparison is numeric. If at least one operand is float, both operands are converted to float before comparison.

8.6.3.2 The result of a comparison is a value of type int, equal to 1 if the comparison is true and 0 if the comparison is false.

8.6.3.3 Comparisons involving NaN are false, except that != involving NaN is true (Section 8.6.4.4).

8.6.3.4 If either operand is string, the comparison is a string comparison (Section 8.6.8).

8.6.3.5 Example:

int a = 3 < 5;       // a = 1
int b = 3 > 5;       // b = 0
int c = 3 <= 3;      // c = 1
int d = 3.5 >= 3;    // d = 1 (3 promoted to 3.0)

8.6.4 Equality Operators on Numeric Operands: ==, !=

8.6.4.1 If both operands are numeric, the comparison is numeric following the same conversion rules as Section 8.6.3.1.

8.6.4.2 If either operand is string, the comparison is a string comparison (Section 8.6.8).

8.6.4.3 The result of an equality comparison is a value of type int, equal to 1 if true and 0 if false.

8.6.4.4 Comparisons involving NaN: == with NaN is false, != with NaN is true.

8.6.5 Truthiness of Binary Results

8.6.5.1 The result of a comparison operator and of a logical operator has type int and is either 0 or 1. This value MAY be used directly as an integer, for example in an arithmetic expression.

8.6.5.2 The result of a comparison is truthy if and only if it equals 1 (Section 3.13).

8.6.6 String Concatenation

8.6.6.1 If at least one operand of + has type string, the operator performs string concatenation.

8.6.6.2 Each operand is first converted to string according to the rules of Section 7.7.1: an int operand is converted to its decimal representation; a float operand is converted according to the N.0 or %g rule; a string operand is used as-is.

8.6.6.3 The result is a newly allocated string containing the bytes of the left operand followed by the bytes of the right operand. The allocation is performed with the C malloc function. The allocated memory is not freed by the runtime; see Section 12.2.

8.6.6.4 Example:

string s = "x = " + 5;             // s is "x = 5"
string t = "pi is " + 3.14;        // t is "pi is 3.14"
string u = "a" + "b" + "c";        // u is "abc"
string v = 1 + " " + 2.0;          // v is "1 2.0"

8.6.7 Truthiness

8.6.7.1 In a context that requires a truth value (the condition of an if, while, do-while, or for statement, the operand of !, or the operand of && or ||), the expression is evaluated to a truth value according to the following rules:

  • An int value is truthy if and only if it is not equal to 0.
  • A float value is truthy if and only if it is not equal to 0.0. NaN is truthy.
  • A string value is truthy if and only if its length is greater than 0. A string consisting of a single null byte is not truthy.
  • An array value in a truthiness context is truthy if and only if its declared length is greater than 0.

8.6.7.2 Example:

if (1)     { print "yes"; }   // prints "yes"
if (0)     { print "yes"; }   // does not print
if (0.0)   { print "yes"; }   // does not print
if ("")    { print "yes"; }   // does not print
if ("a")   { print "yes"; }   // prints "yes"

8.6.8 String Comparison Operators

8.6.8.1 The equality operators == and !=, and the comparison operators <, >, <=, >=, when applied to two operands of type string, compare the byte sequences, not the pointers.

8.6.8.2 The comparison is performed by the C standard library function strcmp, which returns a negative value, zero, or a positive value depending on the lexicographic order of the byte sequences as unsigned characters. The result of the Zeuz operator is a value of type int, equal to 1 if the comparison holds and 0 if it does not.

8.6.8.3 Two string values that point to distinct memory locations but contain the same byte sequence compare equal under ==. Conversely, two string values that point to the same location always compare equal, but this is a consequence of the content being equal, not a separate rule.

8.6.8.4 The operators <, >, <=, >= on strings compare the byte sequences lexicographically. This is not locale-sensitive; it is the C strcmp order.

8.6.8.5 Example:

string a = "hello";
string b = "hello";
string c = "world";
int e = (a == b);    // e = 1; equal byte sequences
int f = (a != c);    // f = 1
int g = (a < c);     // g = 1; "hello" precedes "world"
int h = (c > a);     // h = 1

8.6.9 Division by Zero

8.6.9.1 The operator / performs a runtime check on the right operand. If the right operand is equal to zero (for int) or to 0.0 (for float), the implementation MUST terminate the program with exit code 1 and MUST write the diagnostic message division by zero\n to the standard error stream.

8.6.9.2 The exact bytes written to the standard error stream are division by zero followed by a single newline byte. This is a normative requirement so that a test suite can check for it.

8.6.9.3 The implementation MUST NOT produce a floating-point infinity as the result of division by zero. This differs from IEEE 754 default behavior and from C. Section 2.1 states that this reference takes precedence over LLVM in this regard.

8.6.9.4 The check is performed on every evaluation of the operator, including in dead code that the optimizer might otherwise remove. The implementation MUST NOT optimize away the check.

8.6.9.5 Example:

int a = 10 / 2;      // a = 5
int b = 10 / 0;      // program terminates with exit code 1, stderr: division by zero
float c = 1.0 / 0.0; // program terminates with exit code 1, stderr: division by zero

8.6.10 Logical Operators: && and ||

8.6.10.1 The operators && and || perform short-circuit evaluation. The left operand is evaluated first, converted to a truth value (Section 8.6.7), and the result determines whether the right operand is evaluated.

8.6.10.2 For &&: if the left operand is not truthy, the result is 0 and the right operand is not evaluated. Otherwise the right operand is evaluated, converted to a truth value, and the result is 1 if the right operand is truthy and 0 otherwise.

8.6.10.3 For ||: if the left operand is truthy, the result is 1 and the right operand is not evaluated. Otherwise the right operand is evaluated, converted to a truth value, and the result is 1 if the right operand is truthy and 0 otherwise.

8.6.10.4 The result of && or || has type int and is either 0 or 1.

8.6.10.5 Example:

int a = 1 && 1;    // a = 1
int b = 1 && 0;    // b = 0
int c = 0 || 1;    // c = 1
int d = 0 || 0;    // d = 0

int x = 0;
int e = (x != 0) && (10 / x > 1);  // e = 0; division is not evaluated

8.7 Unary Operators

8.7.1 Arithmetic Negation: -

8.7.1.1 The unary minus operator applies to a numeric operand. If the operand is int, the result is the two's complement negation, well-defined for all values including the most negative value. If the operand is float, the result is the IEEE 754 negation, which flips the sign bit.

8.7.1.2 The unary minus operator applied to a string operand is ill-formed.

8.7.1.3 Example:

int a = -5;         // a = -5
float b = -3.14;    // b = -3.14
float c = -inf;     // c is negative infinity

8.7.2 Logical Negation: !

8.7.2.1 The unary operator ! applies to any operand. The operand is evaluated and converted to a truth value (Section 8.6.7). The result is 1 if the operand is not truthy and 0 if it is truthy.

8.7.2.2 The result has type int.

8.7.2.3 Example:

int a = !0;         // a = 1
int b = !1;         // b = 0
int c = !"";        // c = 1
int d = !"x";       // d = 0
int e = !3.14;      // e = 0

8.8 Assignment Expressions

8.8.1 Assignment to a Variable

8.8.1.1 The assignment expression name = value stores the value of the right operand into the storage location named by name. The identifier name MUST resolve to a variable in scope (Section 10).

8.8.1.2 The value of the assignment expression is the value that was stored, with the type of the variable.

8.8.1.3 If the variable has type float and the right operand has type int, the right operand is converted to float before storage. The value of the assignment expression has type float.

8.8.1.4 If the variable has type int and the right operand has type float, the assignment is ill-formed and MUST be diagnosed. See Section 7.5.2.

8.8.1.5 Assignment to an array variable as a whole is ill-formed and MUST be diagnosed. Individual elements may be assigned via an indexed assignment (Section 8.9).

8.8.1.6 Example:

int x = 0;
int y = (x = 5);        // x is 5, y is 5
float f = 0.0;
float g = (f = 3);      // f is 3.0, g is 3.0
int z = 0;
z = 3.14;               // ill-formed: cannot assign float to int

8.8.2 Assignment as an Expression

8.8.2.1 Because assignment is an expression, it may appear as a subexpression. For example, a = b = c parses as a = (b = c) because assignment is right-associative. The value of the inner assignment is the value stored in b, which is then stored in a.

8.9 Array Index Assignment

8.9.1 The indexed assignment expression name[index] = value stores the value of value into the element of the array name at position index. The identifier name MUST resolve to an array variable in scope. The index expression MUST have type int.

8.9.2 If the array element type is float and the right operand has type int, the right operand is converted to float before storage. If the array element type is int and the right operand has type float, the assignment is ill-formed and MUST be diagnosed.

8.9.3 The value of the indexed assignment expression is the value that was stored.

8.9.4 The index is not bounds-checked. See Section 8.10.4.

8.9.5 Example:

int arr[5];
arr[0] = 10;
arr[1] = arr[0] + 5;    // arr[1] = 15
float fa[3];
fa[0] = 1;              // 1 is converted to 1.0
int x = arr[1];         // x = 15

8.10 Array Indexing

8.10.1 The array indexing expression name[index] evaluates to the element of the array name at position index. When used in a context that requires a value, the result has the element type of the array.

8.10.2 The identifier name MUST resolve to an array variable in scope. The index expression MUST have type int.

8.10.3 The index is evaluated before the element is read.

8.10.4 No bounds check. The implementation MUST NOT insert a runtime bounds check on array indexing, whether for reading or for writing. An index that is negative or greater than or equal to the declared length produces undefined behavior (Section 13.4). A conforming program MUST NOT index outside the declared bounds.

8.10.5 Example:

int arr[3] = {10, 20, 30};
int a = arr[0];      // a = 10
int b = arr[2];      // b = 30
int i = 1;
int c = arr[i];      // c = 20
int d = arr[3];      // undefined behavior: index out of bounds
int e = arr[-1];     // undefined behavior: negative index

8.11 Function Calls

8.11.1 A function call expression has the form name(arg1, arg2, ..., argN), where name is an identifier that resolves to a function declaration in the program, and each argK is an expression. The number of arguments MUST equal the number of parameters declared by the function.

8.11.2 The arguments are evaluated in source order, from left to right. A program MAY rely on this order when the arguments have side effects.

8.11.3 Each argument is converted to the declared type of the corresponding parameter before the call, according to the assignment rules of Section 7.5.

8.11.4 If the parameter is declared as an array parameter (Section 6.3.3), the corresponding argument MUST be an array variable in scope. Passing anything other than a variable name is ill-formed. The array length is not passed.

8.11.5 The type of the call expression is the declared return type of the function.

8.11.6 The implementation MUST permit a call to a function declared later in the source file than the call site (Section 10.5).

8.11.7 Example:

int add(int a, int b) { return a + b; }
int sum(int arr[], int n) {
    int s = 0;
    int i = 0;
    while (i < n) { s = s + arr[i]; i = i + 1; }
    return s;
}

int x = add(2, 3);              // x = 5
int data[3] = {10, 20, 30};
int y = sum(data, 3);           // y = 60
int z = add(2.5, 3);            // ill-formed: 2.5 is float, parameter is int
int w = sum(data[0], 3);        // ill-formed: argument is not an array variable

8.12 Cast Expressions

8.12.1 A cast expression has the form (TypeName) operand, where TypeName is one of the keywords listed in Section 6.5.14 and operand is a unary expression. The cast is right-associative and binds tighter than binary operators.

8.12.2 The cast converts the operand to the named type. The permitted conversions are listed in Section 7.7.1.

8.12.3 The type of the cast expression is the named type. For integer type aliases, the type is int; for float type aliases, the type is float.

8.12.4 Example:

int a = (int) 3.9;            // a = 3 (truncation toward zero)
float b = (float) 7;          // b = 7.0
string c = (string) 42;       // c = "42"
string d = (string) 3.14;     // d = "3.14"
string e = (string) 1.0;      // e = "1.0" (integral float)
float f = (float) "hello";    // ill-formed: cannot cast string to float
int g = (int) "hello";        // ill-formed

9. Statements

9.1 Variable Declaration

9.1.1 Grammar

See production G.6.3.4 and G.6.3.5. A variable declaration has one of the following forms:

TypeName Identifier ;
TypeName Identifier = Expression ;
TypeName Identifier [ Expression ] ;
TypeName Identifier [ Expression ] = { ArrayInit } ;

9.1.2 Scalar Declaration Without Initializer

9.1.2.1 The declaration TypeName name; introduces a variable of the named type with the default value for that type: 0 for int, 0.0 for float, "" (the empty string) for string.

9.1.2.2 Declaring a variable of type void is ill-formed.

9.1.3 Scalar Declaration With Initializer

9.1.3.1 The declaration TypeName name = Expression; introduces a variable with the value of the initializer expression, converted according to the assignment rules of Section 7.5.

9.1.4 Array Declaration

9.1.4.1 The declaration TypeName name[Size]; introduces an array of Size elements, each of the declared type. The size expression MUST have type int.

9.1.4.2 A negative size expression produces a runtime error: the implementation MUST terminate the program with exit code 1 and write negative array size\n to the standard error stream.

9.1.4.3 The elements of an array declared without an initializer list are zero-initialized.

9.1.5 Array Declaration With Initializer List

9.1.5.1 The declaration TypeName name[Size] = {e1, e2, ..., ek}; introduces an array with the value of e1 in position 0, and so on. If k < Size, the remaining elements are zero-initialized. If k > Size, the extra initializers are evaluated and discarded; this behavior is implementation-defined.

9.1.5.2 Each initializer expression MUST be convertible to the element type.

9.1.6 Examples

int a;                          // a = 0
int b = 5;                      // b = 5
float f;                        // f = 0.0
string s;                       // s = ""
int arr[3];                     // arr = {0, 0, 0}
int arr2[3] = {10, 20, 30};     // arr2 = {10, 20, 30}
float fa[2] = {1, 2};           // fa = {1.0, 2.0}
int n = 5;
int vla[n];                     // runtime-sized array of 5 zeros

int bad1 = 3.14;                // ill-formed: float initializer for int
int bad2[2] = {1.0, 2.0};       // ill-formed: float in int array initializer
void bad3;                      // ill-formed: void variable

9.2 Expression Statement

9.2.1 An expression statement is an expression followed by a semicolon. The expression is evaluated and its value is discarded.

x + 1;          // evaluates x + 1, discards the result
x = 5;          // assignment; the result 5 is discarded
f(3);           // function call; the return value is discarded

9.3 Block Statement

9.3.1 A block statement is a sequence of zero or more statements enclosed in braces. The block introduces a new scope (Section 10.1).

{
    int x = 1;
    {
        int x = 2;      // shadows outer x
        print x;        // prints 2
    }
    print x;            // prints 1
}

9.4 If Statement

9.4.1 The if statement has the form if (Cond) ThenStmt or if (Cond) ThenStmt else ElseStmt. The condition is evaluated to a truth value. If the condition is truthy, ThenStmt is executed; otherwise, ElseStmt is executed if present.

9.4.2 Dangling-else ambiguity is resolved by attaching else to the nearest unmatched if.

int x = 10;
if (x > 5) {
    print "greater";
} else if (x == 5) {
    print "equal";
} else {
    print "less";
}

9.5 While Statement

9.5.1 The while statement has the form while (Cond) Body. The condition is evaluated before each iteration. If truthy, the body executes and the loop repeats.

9.5.2 A break statement exits the loop immediately. A continue statement skips the remainder of the current iteration and returns to the condition check.

int i = 0;
while (i < 3) {
    print i;
    i = i + 1;
}
// Output: 0, 1, 2 (each on its own line)

9.6 Do-While Statement

9.6.1 The do-while statement has the form do Body while (Cond);. The body is executed once, then the condition is evaluated. If truthy, the body executes again.

9.6.2 The trailing semicolon after the closing parenthesis is required.

int i = 0;
do {
    print i;
    i = i + 1;
} while (i < 3);
// Output: 0, 1, 2

9.7 For Statement

9.7.1 The for statement has the form for (Init; Cond; Step) Body. The parts are optional. Init is either a variable declaration or an expression statement. Cond is an expression; if omitted, it is always truthy. Step is an expression; if omitted, no step is executed.

9.7.2 Execution order: Init once, then Cond, body, Step, Cond, body, Step, and so on.

9.7.3 The for statement introduces a new scope encompassing Init, Cond, Step, and Body.

for (int i = 0; i < 3; i = i + 1) {
    print i;
}
// Output: 0, 1, 2

int j = 0;
for (; j < 3; j = j + 1) {
    print j;
}
// Output: 0, 1, 2

9.8 Loop Statement

9.8.1 The loop statement has the form loop Body. It executes the body repeatedly without a condition. The loop MUST be exited via break or return.

9.8.2 The loop statement is equivalent to while (1) Body.

int i = 0;
loop {
    if (i >= 3) { break; }
    print i;
    i = i + 1;
}
// Output: 0, 1, 2

9.9 Break and Continue

9.9.1 A break statement terminates execution of the innermost enclosing loop. Control transfers to the statement immediately after the loop.

9.9.2 A continue statement terminates the current iteration of the innermost enclosing loop and begins the next iteration.

9.9.3 A break or continue outside of any loop is ill-formed and MUST be diagnosed.

for (int i = 0; i < 5; i = i + 1) {
    if (i == 2) { continue; }    // skip 2
    if (i == 4) { break; }       // exit at 4
    print i;
}
// Output: 0, 1, 3

9.10 Return Statement

9.10.1 A return statement has the form return; or return Expression;. It terminates execution of the enclosing function.

9.10.2 In a function declared with return type void, a return with an operand is ill-formed.

9.10.3 In a function declared with a non-void return type, a return without an operand is ill-formed.

9.10.4 A function with a non-void return type that falls off the end of its body without a return returns a default value: 0 for int, 0.0 for float, null for string. This behavior is implementation-defined.

9.10.5 Special case: return in entryf. A return statement inside the body of entryf sets the exit code of the program. The return value, if any, is converted to int. A return without an operand sets the exit code to 0.

int add(int a, int b) {
    return a + b;
}

void greet(string name) {
    print "Hello, " + name;
    return;
}

void entryf() {
    int x = add(2, 3);
    greet("world");
    return x;    // sets exit code to 5
}

9.11 Print Statement

9.11.1 A print statement has the form print Expression;. The expression is evaluated and its value is written to the standard output stream, followed by a newline byte.

9.11.2 The format of the output depends on the type of the expression:

  • int: decimal representation, optionally with a leading minus sign.
  • float: if finite and integral, N.0; otherwise the C printf("%g") format.
  • string: the bytes of the string.
  • Array: [, elements separated by , , each formatted per the element type, then ].

9.11.3 The print statement is a statement, not an expression.

print 42;                  // 42
print 3.14;                // 3.14
print 1.0;                 // 1.0
print "hello";             // hello
int arr[3] = {1, 2, 3};
print arr;                 // [1, 2, 3]

9.12 Assert Statement

9.12.1 An assert statement has the form assert(Expression);. The expression is evaluated to a truth value. If not truthy, the implementation MUST write assertion failed at line N\n to the standard error stream and MUST terminate the program with exit code 1.

9.12.2 The line number in the diagnostic is the line of the assert keyword, starting from 1.

9.12.3 The assert statement is not removed in any build configuration.

int x = 5;
assert(x > 0);        // continues
assert(x < 0);        // terminates with exit 1, stderr: assertion failed at line 3

9.13 Function Declaration

9.13.1 A function declaration consists of a return type, an identifier, a parameter list in parentheses, and a body block.

9.13.2 The return type MUST be one of the primitive types listed in Section 6.5.14. In Zeuz 1.0, a function MAY NOT return an array.

9.13.3 Each parameter has a type and an identifier. The identifier MUST be unique within the parameter list.

9.13.4 An array parameter receives a pointer to the first element of the caller's array. The length is not passed. Inside the callee, len(param) on an array parameter is ill-formed. Writing to an element of an array parameter modifies the caller's array.

9.13.5 The body MUST be a block. The body introduces a new scope.

9.13.6 A function MAY be declared after the statements or functions that call it (Section 10.5). A function name MUST NOT be declared twice in the same program.

int factorial(int n) {
    if (n <= 1) { return 1; }
    return n * factorial(n - 1);
}

int sum(int arr[], int n) {
    int s = 0;
    int i = 0;
    while (i < n) {
        s = s + arr[i];
        i = i + 1;
    }
    return s;
}

void entryf() {
    print factorial(5);         // 120
    int data[3] = {1, 2, 3};
    print sum(data, 3);         // 6
}

10. Scoping and Name Resolution

10.1 Block Scope

10.1.1 A block statement, a function body, and a for statement each introduce a new scope. The scope extends from the point of introduction to the end of the block, function body, or for statement.

10.1.2 A variable declared in a scope is visible in that scope and in any nested scope, except where shadowed (Section 10.3).

10.1.3 A variable is not visible in scopes that enclose its declaration.

int x = 1;
{
    int y = 2;
    print x + y;    // 3
}
print y;            // ill-formed: y is not in scope

10.2 Function Scope

10.2.1 Each function body introduces a scope containing the function's parameters and any variables declared directly in the body.

10.2.2 Parameters are visible throughout the body, including in nested blocks, unless shadowed by a local declaration.

10.2.3 Function names are visible throughout the program, regardless of declaration order (Section 10.5).

void f(int a) {
    print a;        // a is the parameter
    {
        int a = 5;  // shadows the parameter
        print a;    // 5
    }
    print a;        // the parameter again
}

10.3 Shadowing

10.3.1 A variable declared in a nested scope MAY have the same name as a variable declared in an enclosing scope. The inner declaration shadows the outer one from the point of declaration to the end of the inner scope.

10.3.2 Shadowing does not produce a diagnostic. It is well-formed.

10.3.3 After the inner scope ends, the outer variable becomes visible again with its previous value.

int x = 1;
{
    int x = 2;
    print x;    // 2
}
print x;        // 1

10.4 Redeclaration

10.4.1 Declaring two variables with the same name in the same scope is ill-formed and MUST be diagnosed.

10.4.2 Declaring two functions with the same name in a program is ill-formed and MUST be diagnosed.

10.4.3 Declaring two parameters with the same name in a function is ill-formed and MUST be diagnosed.

10.4.4 A variable and a function MAY share a name. The two names occupy separate namespaces and are resolved independently.

int x = 1;
int x = 2;          // ill-formed: redeclaration of x

int f() { return 1; }
int f() { return 2; }   // ill-formed: redeclaration of f

10.5 Forward References to Functions

10.5.1 A function call MAY appear before the declaration of the called function in the source file.

10.5.2 The function declaration MUST appear somewhere in the same program.

void entryf() {
    print add(2, 3);    // forward reference, well-formed
}

int add(int a, int b) {
    return a + b;
}

10.6 Forward References to Variables

10.6.1 A variable reference MUST appear after the variable's declaration in the source text.

10.6.2 This rule applies whether or not the reference is inside a nested scope.

void entryf() {
    print x;            // ill-formed: x is not declared before this line
    int x = 5;
    print x;            // 5
}

11. Semantics of Built-in Functions

11.1 print

11.1.1 The print statement writes the value of its expression to the standard output stream followed by a single newline byte (value 10). The exact format depends on the type of the expression as defined in Section 9.11.2.

11.1.2 For a value of type int, the output is the decimal representation of the value, optionally prefixed by a minus sign. Leading zeros are not produced.

11.1.3 For a value of type float, if the value is finite and has no fractional part, the output has the form N.0 where N is the decimal integer part. Otherwise the output is the C printf("%g") format. The values inf, -inf, and nan produce the strings inf, -inf, and nan respectively; the capitalization of these strings is implementation-defined but in the reference implementation is lowercase.

11.1.4 For a value of type string, the output is the byte sequence of the string. The null terminator is not written.

11.1.5 For an array value, the output is a left bracket, the elements formatted by the rules for their element type, separated by , (comma and a single space), and a right bracket. An empty array produces [].

11.1.6 The print statement does not flush the standard output stream. The stream is flushed at program termination, or when the buffer is full, or when the implementation chooses. Programs that require immediate output (for example, to interleave with input prompts) MUST use input, which flushes stdout before reading.

11.1.7 Example:

print 1 + 2;             // 3
print 3.0;               // 3.0
print 3.5;               // 3.5
print "abc" + "def";     // abcdef
int arr[2] = {7, 8};
print arr;               // [7, 8]

11.2 len

11.2.1 The built-in function len returns the length of a value of type string or an array.

11.2.2 For a string value, the result is the number of bytes in the string, excluding the null terminator. The result has type int.

11.2.3 For a local array, the result is the declared length of the array. The result has type int. For an array parameter (Section 9.13.4), len is ill-formed and MUST be diagnosed, because the callee does not know the length.

11.2.4 An argument that is neither a string nor an array is ill-formed.

11.2.5 Example:

string s = "hello";
int a = len(s);          // a = 5
int arr[7];
int b = len(arr);        // b = 7
int c = len("");         // c = 0

int f(int p[]) {
    int n = len(p);      // ill-formed: array parameter has no length
    return n;
}

11.3 input

11.3.1 The built-in function input reads one line from the standard input stream and returns it as a value of type string.

11.3.2 The function takes one argument of type string, the prompt. Before reading, the implementation MUST write the prompt to the standard output stream and flush the stream. If the argument is the empty string, no prompt is written.

11.3.3 The implementation reads bytes from the standard input stream until a line terminator or end of file. The line terminator, if present, is not included in the result. The result is null-terminated. If end of file is reached with no bytes read, the result is the empty string.

11.3.4 The line length is limited by the internal buffer size. In the reference implementation of Zeuz 1.0, the limit is 1023 bytes. A line longer than the limit is read in pieces; the first piece is returned and the remainder is available for the next input call.

11.3.5 The memory for the returned string is allocated with malloc and is not freed by the runtime.

11.3.6 Example:

string name = input("Name: ");
print "Hello, " + name;

11.4 assert

11.4.1 The assert statement evaluates its argument to a truth value. If the value is truthy, execution continues. Otherwise the implementation writes assertion failed at line N\n to the standard error stream, where N is the line number of the assert keyword, and terminates the program with exit code 1.

11.4.2 The assert statement is a statement, not an expression, and cannot be used in an expression context.

11.4.3 The assert statement is not removed in any build configuration.

11.4.4 Example:

int x = 5;
assert(x > 0);        // continues
assert(x < 0);        // terminates with exit 1

12. Memory Model

12.1 Stack Allocation

12.1.1 Variables declared as scalars (of type int, float, or string) are allocated on the stack of the enclosing function. The storage is released automatically when the function returns.

12.1.2 Arrays declared with a constant size are allocated on the stack. Arrays declared with a runtime size (VLA-style) are also allocated on the stack; the size is computed at the point of declaration. The allocation MUST be released when the enclosing function returns.

12.1.3 The initial contents of an array declared without an initializer list are all zero bytes. The initial value of a scalar variable declared without an initializer is the default value for its type (Section 9.1.2).

12.2 Heap Allocation

12.2.1 Values of type string are stored in heap memory allocated with the C malloc function. The following operations allocate heap memory:

  • Evaluation of a string literal. The implementation MAY allocate once per literal or once per evaluation.
  • String concatenation (Section 8.6.6).
  • Casting int or float to string (Section 7.7.1).
  • The built-in input (Section 11.3).

12.2.2 The heap memory allocated by these operations is never freed by the runtime. A program that allocates strings in a loop will leak memory. Zeuz 1.0 has no free operation, no garbage collector, and no ownership system. See Section 14.1.

12.2.3 A program MAY rely on the heap allocation succeeding. If the host system cannot satisfy the allocation, the behavior is undefined.

12.3 Value Semantics

12.3.1 All assignments and argument passes copy the value. For scalars of type int or float, the copy is a bit-for-bit copy of the value. For scalars of type string, the copy is a copy of the pointer, not the byte sequence; both the original variable and the new variable refer to the same heap allocation. Modifying the heap byte sequence through one variable affects the other, but the byte sequence is immutable in the source language, so this is not observable except through the runtime helpers.

12.3.2 Arrays are passed to functions as pointers. The callee sees the caller's array, not a copy. Writing to an element of the array parameter modifies the caller's array.

12.4 Array Layout

12.4.1 A local array is a contiguous sequence of elements of the declared type. The element type has a size determined by the implementation: in the reference implementation, 8 bytes for int and float, 8 bytes for string (a pointer).

12.4.2 The length of a local array is known at the point of declaration and is stored by the implementation for the purpose of len(). The length is not stored in the array itself.

12.4.3 An array parameter does not carry a length. The callee MUST know the length from an additional scalar parameter or from a protocol between caller and callee.

12.4.4 The layout of an array is not part of the source-level contract. A program MUST NOT rely on the size, alignment, or ordering of elements in memory.

12.5 String Representation

12.5.1 A value of type string is a pointer to a byte sequence in heap memory. The byte sequence is null-terminated: the byte after the last meaningful byte is a byte with value 0. The length of the string is the number of bytes before the first null byte.

12.5.2 The byte sequence may contain bytes with value 0 in the middle. In this case the string is truncated at the first null byte for the purpose of len(), string comparison, and print. There is no way to represent a string with an embedded null byte in Zeuz 1.0.

12.5.3 The byte sequence is immutable in the source language. The source language provides no operation that modifies a string's bytes after creation. The runtime helpers create fresh byte sequences for concatenation and conversion.

12.6 Lifetime Rules

12.6.1 A scalar variable's storage is valid from the point of declaration to the end of the enclosing scope. A reference to a variable after its scope has ended is a compile-time error (Section 10.6).

12.6.2 An array's storage is valid from the point of declaration to the end of the enclosing function. Zeuz 1.0 does not support returning an array from a function, so an array never outlives its enclosing function.

12.6.3 A string's heap storage is valid from the point of allocation to program termination. There is no way to free it.

12.7 Known Memory Hazards

12.7.1 Out-of-bounds array indexing (Section 8.10.4) is undefined behavior. A program that indexes outside the declared bounds may crash, produce wrong results, or corrupt memory.

12.7.2 Heap memory is never freed. Programs that allocate strings in loops will consume memory proportionally to the number of iterations.

12.7.3 The runtime does not check for null string pointers. Passing a null pointer to print, len, string comparison, or concatenation is undefined behavior.

12.7.4 Because strings are passed by pointer copy, a program that assigns a string variable to another and then modifies the original's underlying bytes (which the source language does not permit) would observe the change through both variables. This is not a hazard in the source language because the byte sequence is immutable, but it is a property of the memory model that implementers of runtime helpers MUST observe.

13. Program Structure and Execution

13.1 Compilation Unit

13.1.1 A compilation unit is exactly one source file. Zeuz 1.0 has no import, include, or module mechanism. All program text MUST appear in a single source file.

13.1.2 The source file MUST be passed to the compiler as the sole input. The compiler MAY accept command-line options but MUST NOT accept additional source files in the same invocation.

13.2 The entryf Function

13.2.1 A well-formed program MUST declare exactly one function whose name is entryf. The declaration MUST have return type void and MUST have zero parameters. The declaration MAY appear anywhere in the source file.

13.2.2 The body of entryf is the program's entry point. It is executed after any top-level statements that precede the declaration of entryf (but Zeuz 1.0 rejects top-level statements other than function declarations; see Section 13.2.4).

13.2.3 Other functions MAY be called from entryf and from each other. Function declarations MAY appear in any order (Section 10.5).

13.2.4 Top-level statements. In the reference implementation of Zeuz 1.0, top-level statements other than function declarations are rejected. A program consists of function declarations only, of which exactly one is entryf.

13.3 Program Startup and Exit Code

13.3.1 The implementation translates the program to a native binary. When the binary is executed, the operating system enters the C main function generated by the implementation. That function runs the body of entryf.

13.3.2 The value returned by entryf is used as the process exit code, truncated to an int if necessary. The behavior of entryf without an explicit return is to use 0 as the exit code.

13.3.3 A return statement inside entryf terminates the function. A return without an operand uses 0 as the exit code. A return with an operand converts the operand to int: a float is truncated toward zero; a string yields 0.

13.3.4 The process exit code is the low 8 bits of the value returned by entryf, as specified by the host operating system for the C main function.

13.3.5 If the program terminates because of assert, division by zero, negative array size, or an explicit exit in a runtime helper, the exit code is 1.

13.4 Undefined Behavior

13.4.1 The following conditions produce undefined behavior in Zeuz 1.0:

  • Array indexing with an index that is negative or greater than or equal to the declared length (Section 8.10.4).
  • Dereferencing a null string pointer (Section 12.7.3).
  • Reading or writing through a pointer that does not refer to a valid object (for example, after the object's storage has been released).
  • Calling a function with more or fewer arguments than the function declares.

13.4.2 The following conditions that would produce undefined behavior in C do not produce undefined behavior in Zeuz 1.0:

  • Integer overflow is well-defined (Section 8.6.2.4).
  • Division by zero terminates the program with a diagnostic (Section 8.6.9).

13.5 Implementation-Defined Behavior

13.5.1 The following behaviors are implementation-defined in Zeuz 1.0:

  • The exact column at which a token is reported in a diagnostic (Section 5.2.4).
  • The interpretation of non-ASCII bytes in string literals (Section 5.1.3).
  • The rounding mode for float literals and for floating-point arithmetic (Section 5.9.4, Section 8.6.2.5).
  • The behavior of casting NaN, infinity, or an out-of-range float to int (Section 7.7.1).
  • The result of the unary minus operator on NaN (Section 5.13.3).
  • The representation of inf, -inf, and nan produced by print on a value of type float (Section 11.1.3).
  • The behavior of falling off the end of a non-void function (Section 9.10.4).
  • The line length limit for input (Section 11.3.4).
  • The size and alignment of elements in an array (Section 12.4.1).
  • The behavior of allocation failure (Section 12.2.3).

13.5.2 An implementation MUST document its choice for each item in Section 13.5.1.

14. Rationale (Non-Normative)

14.1 Why No Garbage Collector in v1

Zeuz 1.0 targets a single-file, single-translation-unit model with no runtime library beyond the C standard library. A garbage collector would require either a tracing collector (which needs stack maps, precise root identification, and a write barrier) or a reference-counting scheme (which needs compiler-inserted increments and decrements at every pointer copy). Both would substantially increase the implementation complexity of the compiler and the runtime, and both would introduce new failure modes (collector pauses, reference cycles, incorrect stack maps) that the current implementation cannot test. The decision to defer garbage collection is deliberate: it keeps the compiler small enough to be audited, and it makes the memory behavior of every program predictable from the source text. The cost is the leak described in Section 12.2.2, which is documented rather than hidden.

14.2 Why All Integers Collapse to i64

The source language accepts i8, u32, usize, and similar spellings for readability and for compatibility with other languages' type vocabularies. However, the LLVM backend in Zeuz 1.0 emits every integer as i64. Two factors motivate this choice. First, arithmetic on i64 is a single LLVM instruction on every target the reference implementation supports; arithmetic on narrower types would require truncation and extension instructions on every operation, which complicates code generation and debugging. Second, having a single integer representation means that the semantics of integer operations are uniform: there is no need to document the promotion rules, the wrapping behavior at each width, or the interaction between signed and unsigned representations. The limitation, which is documented in Section 7.2.2, is that the width and signedness spelled by the programmer are not enforced. A program that requires the exact behavior of u8 arithmetic MUST perform the truncation manually.

14.3 Why String Comparison Uses strcmp

Zeuz 1.0 has no pointer identity operator. A programmer who writes if (a == b) for two strings almost certainly means "are the byte sequences equal", not "are the pointers equal". Using pointer identity would produce surprising results for string literals that the implementation chooses to deduplicate or not, and for strings produced by separate calls to input or to concatenation. Using strcmp matches the programmer's intent and matches the behavior of the == operator on strings in most languages the target audience is familiar with. The cost is that string comparison is O(n) in the length of the strings, and that a program cannot test pointer identity even if it wants to. Neither of these is a limitation the language is likely to lift; if pointer identity is needed, the language would need an explicit operator, not a change to ==.

14.4 Why entryf Instead of main

The name entryf is chosen to make the distinction between the source-level entry point and the C-level main function explicit. The compiler emits a C main that calls the body of entryf and returns its result as the exit code. Naming the source-level function main would create an ambiguity: does the programmer mean the C main with its argc/argv arguments and its int return type, or does the programmer mean a Zeuz function? By using a distinct name, the reference avoids any possibility of collision and makes the translation explicit.

14.5 Why No Module System

A module system requires resolving names across files, which requires a convention for file paths, a convention for what is exported, and a mechanism for the compiler to locate the files. All three are environment-dependent. Zeuz 1.0 avoids this by requiring all program text in one file. The cost is that programs cannot be split into reusable libraries, which limits the size of program that can be written comfortably. The reserved keywords import, namespace, and export are placeholders for a future module system; until that system is specified, they produce a diagnostic when used.

14.6 Why AOT Only

The compiler emits a native binary before execution. There is no interpreter mode and no JIT. AOT compilation has the advantage that the compiled program's performance is predictable and that the compiler's output can be inspected with standard tools (objdump, gdb, perf). It has the disadvantage that the programmer cannot use the language interactively, which would be useful for small experiments and for teaching. A future revision MAY add an interpreter mode; the language semantics are defined independently of the execution mode, so an interpreter would be a conforming implementation.

15. Future Directions (Non-Normative)

15.1 Reserved Features

The keywords in Section 5.7 are reserved for features that the working group intends to add. The working group's current priorities, in rough order, are:

  1. A module system, so that programs can be split into files.
  2. Pattern matching and algebraic data types, using match, case, and enum.
  3. Error handling, using try, catch, throw, and possibly defer.
  4. A minimal form of generics or type parameters, so that data structures can be written once.
  5. Pointer and reference syntax, for programs that need to share mutable state without passing arrays.

The working group does not commit to any of these features, nor to any timeline. A keyword's presence in Section 5.7 means only that the working group has considered the feature and does not want its name taken by user code.

15.2 Possible Memory Model Changes

Two changes to the memory model are under consideration:

  1. A reference-counting scheme for strings, which would allow a program to release string memory deterministically. This would change the value semantics of strings from pointer-copy to reference-count-copy and would require a way to indicate ownership transfer in the source language.
  2. A bounds-checked array mode, in which array indexing performs a runtime check. This would be a per-array or per-program option, not the default, because the performance cost is significant for programs that already respect bounds.

Neither change is scheduled. A program written for Zeuz 1.0 that does not depend on the exact heap layout will be source-compatible with either change.

15.3 Backward Compatibility Policy

The working group's policy is that a program that is well-formed under version 1.x remains well-formed under any later version 1.y, and produces the same observable behavior, except where the later version adds a new feature that uses a reserved keyword. The reserved keywords in Section 5.7 are exactly those that the working group expects to use in a future feature; a program that uses a reserved keyword as an identifier is already ill-formed under version 1.0, so a later version that gives the keyword a meaning does not break any existing program.

A change to the memory model that removes the leak described in Section 12.2.2 would be source-compatible but not binary-compatible. A program that relies on the leak (for example, by assuming that a string remains valid after the function that produced it has returned) is relying on behavior that Section 12.6.3 defines as valid for the lifetime of the process. If a later version shortens the lifetime, that program would break. The working group will document such a change and will provide a migration path.

Appendix E: Differences from C

Zeuz 1.0 is inspired by C but differs from it in several ways. The following list enumerates the differences that are most likely to surprise a programmer coming from C:

  1. Entry point is void entryf(), not int main(int argc, char** argv). See Section 13.2.
  2. Boolean values are spelled true and false and are integer literals 1 and 0. There is no bool type distinct from int (Section 7.2.1).
  3. All integer types are 64-bit signed. Width and signedness of i8, u32, and similar are not enforced (Section 7.2.2).
  4. Integer overflow wraps silently. There is no undefined behavior for overflow (Section 8.6.2.4).
  5. Division by zero terminates the program with exit code 1 and a diagnostic, for both int and float. C's floating-point division by zero produces infinity (Section 8.6.9).
  6. == on strings compares byte sequences via strcmp, not pointers (Section 8.6.8).
  7. String concatenation is +, not strcat (Section 8.6.6).
  8. Implicit conversion from int to string in concatenation and in casts (Section 7.7.1).
  9. Arrays carry a length, but only for local arrays; array parameters do not (Section 9.13.4).
  10. No pointer syntax. Arrays are passed as pointers implicitly when declared with [] (Section 6.3.3).
  11. No switch, goto, struct, enum, or union. The keywords exist as reserved words (Section 5.7) but produce a diagnostic when used.
  12. No #include or preprocessor. All program text in one file.
  13. print is a statement, not a function (Section 9.11).
  14. assert is a statement, not a macro (Section 9.12).
  15. input is a built-in function, not a library function (Section 11.3).
  16. No garbage collector, no free. Strings allocated by concatenation, cast, or input are never released (Section 12.2.2).
  17. Nested block comments are supported (Section 5.3.3). C does not support nested block comments.
  18. No hexadecimal, octal, or binary integer literals (Section 5.8.2).
  19. No exponent notation for float literals (Section 5.9.2).
  20. Character literals have type int and are not distinct from integers (Section 8.4).
